# 0001 · 执行器永不抛异常

**日期**：2026-09-19
**状态**：生效中

## 背景

`run_task` 的调用方最终会是任务队列的 worker 和 agent loop。命令可能顺利跑完、可能自己失败（非零退出码）、可能超时、也可能压根启动不起来（比如命令拼错了）。这几种情况都要有一个说法，问题是：用异常表达，还是用返回值表达？

## 选项

1. **失败时抛异常**——顺利就返回结果，出问题就 `raise`，调用方写 `try/except` 接。
2. **一律返回结构化结果**（`TaskResult`），用字段（`exit_code`、`timed_out`）区分是哪种情况，永不 `raise`。

## 决定

选 2。`run_task` 内部用 `try/except` 接住 `TimeoutExpired` 和 `OSError`，全部转成 `TaskResult` 返回。命令自己失败（退出码非零）本来就不会让 `subprocess.run` 抛异常，直接原样记录。

## 理由

任务平台里"失败"是常态，不是异常状况——一天跑几千个任务，有的超时、有的报错，这些都是要被路由、被重试、被记录的正常数据，不该走"程序出错了"的异常通道。统一成一种返回形状后，调用方只有一条代码路径：看 `exit_code` 和 `timed_out` 两个字段决定下一步（重试？降级？告警？），不用为"正常失败"和"意外崩溃"分别写处理逻辑。

## 代价

1. **没写兜底 `except Exception`**——如果执行器自己有 bug（比如某处笔误），这个异常不会被吞掉，会直接炸出来。这是刻意的：宁可让 bug 暴露、有调用栈可查，也不要用一个模糊的"内部错误"把线索抹掉。等到第 11 课讲稳定性工程，会补上兜底 + 日志记录，两头兼顾。
2. **丢掉了异常自带的调用栈**——`TimeoutExpired`/`OSError` 被转成 `TaskResult` 后，原始异常的堆栈信息就不在返回值里了。调用方拿到的只有 `stderr` 字符串，排查起来不如原始异常直观。这个代价目前接受，因为换来的是调用方代码的简单。
3. **孙进程杀不掉**（Step 4 实验验证）——`subprocess.run` 超时只会 `kill()` 直接子进程；如果这条命令自己又起了一个进程（比如 `bash deploy.sh` 里启动了后台服务），那个"孙进程"会在超时后继续活着。v0 阶段不处理这个缺口，留到第 13 课上 Docker 沙箱时一并解决（整个容器销毁，比追杀单个进程更彻底）。
